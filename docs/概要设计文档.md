## 1. 设计概述

### 1.1 设计目标

依据《需求文档 v2.0》，交付一个**单进程、跨平台、多连接**的 QQ 聊天机器人后台客户端。核心设计目标：

1. **多连接后台**：以「连接（Connection）」为一级实体，一个控制台管理多个 QQ 连接（多个官方 bot / 多个登录 QQ 号），每连接独立配置、独立运行、独立统计。
2. **单进程一体化**：Web 后台 + 连接管理器 + 核心链路 + LLM 网关 + SQLite 在一个进程内。
3. **连接器可插拔**：官方机器人 / 登录 QQ 号两种接入统一抽象，同一进程可并存多个连接器实例。
4. **连接级隔离**：每连接独立的人格绑定、白黑名单、上下文、流量控制、打点。
5. **跨平台发行**：Windows 安装版 + 便携版；Linux 纯后台 + systemd。
6. **可观测**：结构化打点（带 `connection_id`）→ SQLite → 全局/单连接双视图；日志按连接筛选。
7. **零鉴权人格**：人格为全局资源池，导入即用。

### 1.2 设计原则

| 原则 | 说明 |
| --- | --- |
| 连接即边界 | 「连接」是配置、运行、流量控制、打点、统计的最小边界 |
| 单一配置源 | 全局配置 + 连接级配置统一落 `config.json`，运行时读取 |
| 渠道无关 | 连接器归一化消息模型，核心链路不感知「官方 bot / 登录 QQ 号」差异 |
| 打点即事实 | 每次消息、LLM 调用、连接事件都产出结构化事件（带 `connection_id`），统计由事件聚合 |
| 数据与程序分离 | 用户数据与程序文件分离，便于升级/卸载/迁移 |
| 最小权限 | 默认监听 `127.0.0.1`；密钥加密；对象标识哈希脱敏 |

### 1.3 术语

沿用《需求文档 v2.0》第 3 节。关键新增：

| 术语 | 定义 |
| --- | --- |
| 连接管理器（ConnectionManager） | 维护多个连接器实例，统一生命周期（创建/删除/启停/全部启停）与状态 |
| 连接运行时（ConnectionRuntime） | 一个连接在内存中的运行态：连接器 + 独立核心链路 + 独立上下文 + 独立流量控制 |
| 核心链路（Pipeline） | 消息处理管道，**每连接一个独立实例** |
| 事件总线（EventBus） | 进程内发布/订阅，打点事件统一带 `connection_id` |
| 归一化消息（NormalizedMessage） | 连接器上报的统一消息结构（含 `connectionId`） |

## 3. 模块详细设计

### 3.1 数据层（db）

- 初始化 `node:sqlite`，`PRAGMA journal_mode=WAL`；启动执行版本化迁移。
- Repository 层：`ConnectionRepo` / `MessageRepo` / `LlmCallRepo` / `ConnectionEventRepo` / `AbuseRepo` / `PersonaRepo` / `BanwordRepo` 等，统一入口。
- 所有运行数据表的 Repository 方法均接受 `connectionId?` 过滤参数。

**数据库迁移（触发时机 + 旧库兼容）**：

| 项 | 设计 |
| --- | --- |
| 触发时机 | 服务启动早期（加载配置、创建连接管理器**之前**）执行迁移 |
| 版本记录 | 用 `PRAGMA user_version` 记录当前 schema 版本 |
| 迁移链 | `db/migrations/` 下按版本号递增（`001_init.sql`、`002_add_connection.sql`…），依次执行 `user_version` 之后的脚本 |
| 旧库兼容 | 升级前自动备份旧库为 `client.db.bak.<timestamp>`；脚本按「增量迁移」编写（只增列/表，避免破坏性变更）；迁移失败回滚事务并报错，**不进入运行态** |
| 幂等 | 每个迁移脚本对应一个版本号，已执行版本跳过，重复启动不重复执行 |

### 3.2 事件总线（events）

```ts
type MetricEvent =
  | { kind: 'message'; connectionId; channel; fromHash; groupHash; direction; content; reply; finishReason; latencyMs; promptTokens; completionTokens; llmMs; llmAttempts; persona; sessionId; msgId }
  | { kind: 'llm_call'; connectionId; model; promptTokens; completionTokens; latencyMs; status; retryCnt; error; sessionId }
  | { kind: 'connection'; connectionId; event: 'connect'|'disconnect'|'heartbeat'|'error'; connectorType; detail }
  | { kind: 'abuse'; connectionId; fromHash; reason; kind }
  | { kind: 'log'; connectionId?; level; source; msg; meta };
```

**消费者**：① `metrics.ingest` 落 SQLite；② `log.service` 结构化日志；③ `server.ws.broadcast` 推前端。

### 3.3 连接管理器与连接器（manager + connectors）

**连接运行时**（每个连接一份，内存态）：

```ts
interface ConnectionRuntime {
  connectionId: string;
  config: ConnectionConfig;
  connector: Connector;                    // 连接器实例
  pipeline: Pipeline;                      // 独立核心链路
  contextStore: Map<CtxKey, ContextBuffer>; // 独立上下文缓存
  limiter: RateLimiter;                    // 独立频率控制
  tokenBudget: TokenBudget;                // 独立每日预算计数
  status: ConnectionStatus;                // stopped|starting|running|error
}
```

**连接管理器**：

```ts
interface ConnectionManager {
  create(cfg: ConnectionConfig): ConnectionRuntime;
  remove(connectionId: string): Promise<void>;
  start(connectionId: string): Promise<void>;
  stop(connectionId: string): Promise<void>;
  startAll(): Promise<void>;
  stopAll(): Promise<void>;
  get(connectionId: string): ConnectionRuntime | undefined;
  list(): ConnectionRuntime[];
  status(connectionId: string): ConnectionStatus;
}
```

- 启动：从配置构造 `ConnectionRuntime` → 创建连接器实例与 pipeline → `connector.connect()` → 状态转 `running`；任一连接启动失败**不影响其他连接**。
- 删除：先停止，再释放上下文/预算/连接器资源，最后删配置与关联数据（按保留策略）。

**连接器接口**（渠道无关）：

```ts
interface Connector {
  readonly type: 'official' | 'account';
  connect(cfg: ConnectorConfig): Promise<void>;
  disconnect(): Promise<void>;
  status(): ConnectorStatus;               // connecting|connected|disconnected|error
  onMessage(h: (m: NormalizedMessage) => void): void;
  onStatus(h: (s: ConnectorStatus) => void): void;
  sendReply(r: ReplyPayload): Promise<void>;
}

interface NormalizedMessage {
  connectionId: string;    // 由连接器注入
  channel: 'group' | 'c2c';
  fromId: string;          // 入库前哈希
  groupId?: string;
  messageId: string;
  content: string;         // 已剥离 @ 片段
  atBot: boolean;
}
```

- **OfficialBotConnector**：`qq-official-bot` / 官方 Node SDK，`appId + appSecret`；订阅群 @、私聊意图；被动回复 `msg_id + msg_seq` 幂等；空回复兜底。
- **AccountLoginConnector**：OneBot v11 协议（正向/反向 WS），对接 NapCat；处理 `message.group/private` 事件，剥离 `[CQ:at]`；`send_msg` 发送。
- **消息去重**：每个连接器实例维护独立的 `msg_id → 首次时间` TTL 缓存（默认 600s / 5000 条）。

**登录 QQ 号风险确认（业务约束，对应需求 FR2.3）**：
- 连接 `type === 'account'` 时，配置须含 `riskConfirmed: true`（用户已确认知晓封号风险）。
- 前端：新建/编辑连接选择「登录 QQ 号」时，弹窗提示封号风险，用户勾选确认后才允许保存。
- 后端 `ConnectionService.create/update/start` 校验：`type === 'account'` 且 `riskConfirmed !== true` → 拒绝操作并返回错误码，禁止保存/启动。
- 连接级配置中的 `trigger`（需求 FR3.4）与 `llmOverride`（需求 FR2.3）为 **P1 字段**，P0 不实现。

### 3.4 核心链路（pipeline，每连接独立）

```
NormalizedMessage
  ├─ ① TriggerDecision   [P1] 触发模式（仅@/关键词/概率/静默）；P0 固定「仅 @ 回复」
  ├─ ② AccessControl     本连接的白/黑名单（群+对象）
  ├─ ③ ContextManager    本连接的 contextStore（ring buffer + TTL）
  ├─ ④ SafetyFilter(in)  输入脱敏 + 违禁词（本连接人格红线词 + 全局词）
  ├─ ⑤ PromptBuilder     本连接绑定人格的 profilePrompt + 上下文 + 用户消息
  ├─ ⑥ LLM Gateway       调用 + 重试 + token 统计（本连接的 LLM 配置或全局默认）
  ├─ ⑦ SafetyFilter(out) 输出违禁词 → 命中替换兜底
  └─ ⑧ Reply             sendReply → 打点 message 事件（带 connectionId）
```

- Pipeline 为**工厂创建**：`PipelineFactory.create(runtime)`，每个运行时持有独立状态（上下文/预算/限流）。
- 异常兜底：LLM 失败返回预设兜底语（`finishReason: error`），不影响进程与其他连接。

### 3.5 LLM 网关（llm）

```ts
interface LlmResult { ok: boolean; stub: boolean; text: string;
  promptTokens: number; completionTokens: number; attempts: number; elapsedMs: number; }
```

- OpenAI 兼容 `/chat/completions`，兼容「基址 `…/v1`」与「完整地址」。
- 5xx / 超时 / 连接异常重试（≤3 次，指数退避）；4xx 不重试。
- `apiKey` 缺失降级「演示 stub」。
- 每次调用产出 `llm_call` 事件（含 token、耗时、重试、状态，带 connectionId）。
- **配置解析优先级**：连接级 `llmOverride` > 全局 `llm`。

### 3.7 日志模块（log）

- 结构化日志：`{ ts, level, source(server|connector|llm|pipeline), connectionId?, msg, meta }`。
- 内存环形缓冲（最近 4000 行）+ 文件滚动（按 `connectionId + source` 分文件、按天滚动）。
- WS 实时推送（递增 `seq` 游标，断线可续）；前端按连接/来源/级别/关键字筛选。

### 3.8 指标聚合（metrics）

- 由 `message_log` / `llm_call` / `connection_event` / `abuse_event` 聚合查询，不另存冗余表。
- 所有聚合方法接受 `connectionId?`（缺省=全部连接汇总）。
- 时间分桶：小时（今日）/ 天（7d/30d）。
- 成本：`cost = (prompt_tokens × inputPrice + completion_tokens × outputPrice) / 1e6`。

## 4. 核心数据流与时序

### 4.1 消息处理时序（多连接）

```
群用户 ──(群消息@bot)──► 连接器实例(连接1) ──(NormalizedMessage)──► 连接1的Pipeline
        （连接2/3 的流量走各自连接器实例，互不干扰）                        │
                                                                        │
          ①触发决策 → ②白黑名单 → ③上下文 → ④安全(入) → ⑤组装prompt
                │                                            │
                ▼                                            ▼
              忽略/不响应                         ⑥ LLM网关 ──HTTP──► 大模型API
                                                              │ 返回
                                           ⑦安全(出) ◄────────┘
                                                              │
          群用户 ◄──回复── 连接器(连接1) ◄──ReplyPayload── ⑧回复
                                                              │
                                  事件总线(带connectionId) ──► SQLite + WS + 日志文件
```

### 4.2 连接启动 / 停止流程

```
启动：ConnectionService.start(connectionId)
  ├─ precheck() → PrecheckResult（见 4.2.1）
  ├─ 存在 block 失败 → 拒绝启动，返回错误列表；仅 warn → 放行（前端提示）
  ├─ manager.start()：构建 ConnectionRuntime → connector.connect() → status=running
  ├─ 落 run_session(start)
  └─ 失败：记录原因 → status=error（不影响其他连接）

停止：ConnectionService.stop(connectionId)
  ├─ connector.disconnect() → 释放 contextStore / tokenBudget
  ├─ run_session.end_at = now
  └─ status=stopped

全部启动/停止：startAll()/stopAll() 遍历 manager.list()
```

#### 4.2.1 启动预检（Precheck）规范

```ts
interface PrecheckItem {
  key: string;          // credential | dependency | persona | llm
  level: 'block' | 'warn';
  status: 'pass' | 'fail';
  message: string;      // 中文，含原因 + 建议操作
}
interface PrecheckResult { ok: boolean; items: PrecheckItem[]; }  // ok = 无 block 失败
```

| 预检项 | key | 级别 | 失败场景与 `message` 示例 |
| --- | --- | --- | --- |
| 连接凭据 | `credential` | **block（阻塞）** | official 缺 `appId/appSecret` 或 account 缺 `host` → 「连接凭据不完整：请填写 AppID/AppSecret（或 OneBot 地址）」 |
| 依赖可用 | `dependency` | **block（阻塞）** | 官方 SDK 未安装 / NapCat 未运行 → 「连接依赖不可用：请安装官方 SDK / 启动 NapCat」 |
| 人格有效 | `persona` | **block（阻塞）** | `personaId` 不存在或校验失败 → 「绑定人格无效：请重新选择人格」 |
| LLM 连通 | `llm` | **warn（警告放行）** | `apiKey` 未配置 → 降级「演示 stub」仍可启动；连通测试失败 → 「LLM 暂不可用，回复将走兜底」，仍放行 |

- 前端按 `level` 分组展示：**block 失败红色并禁用启动**；**warn 黄色提示但允许启动**。
- 返回结构统一为 `{ code, data: PrecheckResult, message }`；block 失败时 `code` 非 0。

### 4.3 更新检测流程

```
启动(可选) / 手动 → UpdateService.check()
  ├─ 拉取 GitHub Release 最新版 GET /repos/{owner}/{repo}/releases/latest（超时 5s，失败不阻塞）
  ├─ 比较 tag_name vs 当前版本
  ├─ 有新版 → WS 推送横幅 {version, changelog(release body), asset 下载地址}
  └─ 下载升级(P1)：下载 asset → sha256 校验 → 提示替换/执行升级脚本
```

## 5. 数据模型设计（SQLite）

> 含 `connection`（连接）、`persona`（人格主体）、`banword`（全局词库）等表；所有运行数据表带 `connection_id`。对象标识 `sha256` 前 12 位短哈希。

```sql
CREATE TABLE IF NOT EXISTS connection (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id TEXT UNIQUE NOT NULL,       -- 稳定唯一标识
  name          TEXT NOT NULL,
  type          TEXT NOT NULL,              -- official | account
  status        TEXT,                       -- stopped|running|error
  persona_id    TEXT,                       -- 绑定人格
  config_json   TEXT,                       -- 连接级配置（脱敏，含 riskConfirmed）
  created_at    INTEGER,
  updated_at    INTEGER
);

-- 人格主体表（主存储，content_json 为完整档案）；personas/ 目录仅作导入导出与内置默认载体
CREATE TABLE IF NOT EXISTS persona (
  id           TEXT PRIMARY KEY,            -- persona_id
  name         TEXT NOT NULL,
  content_json TEXT NOT NULL,               -- 完整人格档案 JSON
  builtin      INTEGER DEFAULT 0,           -- 是否内置（内置不可删）
  created_at   INTEGER,
  updated_at   INTEGER
);

-- 全局安全过滤词库（SafetyFilter 合并「全局词表 + 绑定人格 bannedWords」）
CREATE TABLE IF NOT EXISTS banword (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  word       TEXT NOT NULL UNIQUE,
  direction  TEXT DEFAULT 'both',           -- in | out | both
  enabled    INTEGER DEFAULT 1,
  created_at INTEGER
);

CREATE TABLE IF NOT EXISTS run_session (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id  TEXT NOT NULL,
  start_at       INTEGER NOT NULL,
  end_at         INTEGER,
  connector_type TEXT,
  persona        TEXT,
  model          TEXT,
  status         TEXT
);
CREATE INDEX idx_session_conn ON run_session(connection_id);

CREATE TABLE IF NOT EXISTS message_log (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id     TEXT NOT NULL,
  session_id        INTEGER,
  ts                INTEGER NOT NULL,
  channel           TEXT,                   -- group | c2c
  from_hash         TEXT,
  group_hash        TEXT,
  direction         TEXT,                   -- in | out
  content           TEXT,
  reply             TEXT,
  finish_reason     TEXT,
  latency_ms        INTEGER,
  llm_ms            INTEGER,
  llm_attempts      INTEGER,
  prompt_tokens     INTEGER,
  completion_tokens INTEGER,
  msg_id            TEXT
);
CREATE INDEX idx_msg_conn ON message_log(connection_id);
CREATE INDEX idx_msg_ts   ON message_log(ts);
CREATE INDEX idx_msg_from ON message_log(from_hash);

CREATE TABLE IF NOT EXISTS llm_call (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id     TEXT NOT NULL,
  session_id        INTEGER,
  ts                INTEGER NOT NULL,
  model             TEXT,
  prompt_tokens     INTEGER,
  completion_tokens INTEGER,
  latency_ms        INTEGER,
  status            TEXT,
  retry_cnt         INTEGER,
  error             TEXT
);
CREATE INDEX idx_llm_conn ON llm_call(connection_id);
CREATE INDEX idx_llm_ts   ON llm_call(ts);

CREATE TABLE IF NOT EXISTS connection_event (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id  TEXT NOT NULL,
  ts             INTEGER NOT NULL,
  event          TEXT,                      -- connect|disconnect|heartbeat|error
  connector_type TEXT,
  detail         TEXT
);

CREATE TABLE IF NOT EXISTS abuse_event (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id TEXT NOT NULL,
  ts            INTEGER NOT NULL,
  from_hash     TEXT,
  reason        TEXT,
  kind          TEXT                        -- flood|over_len|budget|rate
);

CREATE TABLE IF NOT EXISTS persona_snapshot (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  ts         INTEGER NOT NULL,
  persona_id TEXT,
  name       TEXT,
  note       TEXT
);

CREATE TABLE IF NOT EXISTS config_snapshot (
  id    INTEGER PRIMARY KEY AUTOINCREMENT,
  ts    INTEGER NOT NULL,
  scope TEXT,                               -- global | connection:<id>
  json  TEXT,                               -- 脱敏
  note  TEXT
);

CREATE TABLE IF NOT EXISTS app_meta (
  key   TEXT PRIMARY KEY,
  value TEXT                                -- version / update_url / max_connections
);
```

**保留策略**：按 `historyRetentionDays` / `logRetentionDays` 清理运行数据与日志文件。

## 7. 关键机制设计

### 7.1 打点协议

沿用参考项目 `[METRIC]/[ACCESS]` 思想，单进程下改为**进程内事件总线**，所有事件带 `connection_id`；保留可选 stdout 结构化输出便于脱离 UI 排查。

### 7.2 成本折算

- 单价配置：`pricing: { "<model>": { inputPrice, outputPrice } }`（元/百万 token），可全局或连接级覆盖。
- `cost = (promptTokens × inputPrice + completionTokens × outputPrice) / 1_000_000`。

### 7.3 密钥加密（SecretStore）

- 接口 `SecretStore.get/set`；Windows 用 `safeStorage`（Electron）/ DPAPI / `keytar`；Linux 用 keyring 或文件权限 `0600` + 可选加密。
- `config.json` 中密钥仅存密文，不落明文。

### 7.4 上下文管理（每连接）

- `ConnectionRuntime.contextStore: Map<CtxKey, ContextBuffer>`，`CtxKey = channel + ':' + (groupId ?? fromId)`。
- `ContextBuffer`：固定容量 ring buffer（`contextMaxMessages`），TTL 过期清空（`contextTtlMinutes`）。
- 停止连接时整体释放该连接的 `contextStore`。

### 7.5 流量控制（每连接）

- `ConnectionRuntime.limiter`：单位时间最大回复次数 / 消息间隔。
- `ConnectionRuntime.tokenBudget`：每对象每日 token 计数（内存 + 落库，按 `dailyTokenBudget` 熔断）。
- 命中限制 → 兜底回复 + `abuse_event`（带 connectionId）。

### 7.6 幂等去重（每连接）

- 每连接器实例独立 `SeenMessages`（`msg_id → 首次时间` TTL 缓存），重复推送忽略。

### 7.7 内容安全

- `SafetyFilter`：输入脱敏（手机号/身份证）+ 双向词过滤；词来源 = **全局词库 `banword` 表 + 绑定人格 `bannedWords`**，命中即拒绝/兜底。

### 7.8 配置快照脱敏逻辑

- 触发：每次 `ConfigService.save`（全局或连接级）成功后写入一条 `config_snapshot`。
- 脱敏规则（`redact(config)` 递归处理）：

  | 字段 | 处理 |
  | --- | --- |
  | 密钥类 `apiKey` / `appSecret` / `accessToken` / `botToken` | 替换为 `***`（不落明文） |
  | 对象标识 openid / QQ 号 | 短哈希（`sha256` 前 12 位） |
  | 其余字段（模型名、阈值、白名单数量、开关等） | 保留原文 |

- 目的：可追溯「何时改了什么」，但不泄露密钥与隐私。

### 8.1 Windows 发行

| 形态 | 打包方式 | 说明 |
| --- | --- | --- |
| 便携版 | Node SEA 单文件 | 前端静态资源随 assets 打入；数据存同目录 `data\` |

### 8.2 Linux 发行

- Node 直跑：`node dist/main.js --port 8700`，纯后台。
- systemd unit 示例：

```ini
[Unit]
Description=QQ AI ChatBot
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/node /opt/qqaichatbot/dist/main.js --port 8700
Restart=on-failure
RestartSec=5
User=qqaichatbot

[Install]
WantedBy=multi-user.target
```

### 8.3 更新发布（GitHub Release）

- 更新源：**GitHub Release**（`GET https://api.github.com/repos/<owner>/<repo>/releases/latest`）。
- 每个 Release 附平台产物 asset 及校验文件：

  | asset | 说明 |
  | --- | --- |
  | `QQAiChatBot-setup-<ver>.exe` | Windows 安装版 |
  | `QQAiChatBot-portable-<ver>.exe` | Windows 便携版 |
  | `QQAiChatBot-linux-<ver>.tar.gz` | Linux 包 |
  | `*.sha256` | 各产物的 SHA-256 校验值 |

- 版本号取 `tag_name`（如 `v0.1.0`），更新说明取 `body`，下载地址取 asset 的 `browser_download_url`。
- 发布流程：`git tag` → 推送 → 创建 GitHub Release 并上传产物 → 客户端检测到新版本。

## 10. 安全设计

| 项 | 措施 |
| --- | --- |
| 监听 | 默认 `127.0.0.1`；外网访问（`server.allowLan`）开启时**强制要求**配置 `server.accessToken`（≥8 位），外部请求需携带 `Authorization: Bearer <token>`，否则返回 401；未配置 token 时禁止开启外网访问 |
| 密钥 | `SecretStore` 加密存储，`config.json` 不落明文 |
| 隐私 | 对象标识哈希；数据仅本地；支持按对象删除 |
| 内容 | 输入输出双向安全过滤 + 人格红线词 |
| 风控 | 登录 QQ 号方式每连接独立限流 + 用户确认知晓风险 |
| 进程 | Linux 专用用户运行；连接实例轻量化，限制最大连接数 |

## 12. 开放问题

1. **原生窗口选型**：Tauri（轻量，需 Rust）vs Electron（重，纯 JS）vs Neutralino，需在详细设计前定稿。
2. **官方 Node SDK 稳定性**：官方 SDK 更新节奏与 `qq-official-bot` 社区维护度需技术预研验证。
3. **`node:sqlite` flag**：Node 22 需 `--experimental-sqlite`，建议基线定为 Node 24 LTS。
4. **登录 QQ 号协议细节**：NapCat 不同实现字段差异，需连接器兼容层与联调。
5. **代码签名证书**：安装版数字签名需证书成本。
6. **最大连接数**：单进程承载的连接数上限需实测（受内存/WS 连接/系统句柄限制），P0 建议设可配上限。
7. **统计默认视图**：全局汇总 vs 单连接，前端交互需与需求方确认最终偏好。
8. **GitHub Release 私有仓库**：若仓库为 private，`releases/latest` 接口需携带访问 token，需明确更新源的鉴权方案（公开仓库无此问题）。
