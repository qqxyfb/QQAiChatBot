### T01 · 私聊不受 `at` 触发规则限制

- **优先级**：P0　**来源**：TODO 问题 3 根因 B
- **现象**：连接 running、LLM 已配置，私聊给 Bot 发消息完全无反应（不是兜底语，是完全静默）。
- **根因**：`src/pipeline/steps.ts:20` 的 `at` 模式 `return m.atBot`；而 `src/connectors/official.ts:160-171` 对 `C2C_MESSAGE_CREATE` 显式设置 `atBot: false`，私聊必然被 `src/pipeline/index.ts:44` 静默 return。
- **改动清单**
  1. `src/pipeline/steps.ts:20`：`return m.atBot;` → `return m.atBot || m.channel === 'c2c';`
  2. `src/pipeline/steps.ts:11-19`：`keyword` / `random` 两种模式同样补 `|| m.channel === 'c2c'`（私聊语义上无需 @，也不该被概率漏掉）。
  3. 不改 `official.ts` 的 `atBot: false`（保留真实语义，判断收敛到触发层）。
- **验收标准**
  - [ ] 私聊发送任意文本，必有一条回复（正常回复或兜底语）。
  - [ ] 群聊未 @ Bot 时仍不回复（回归）。
  - [ ] `trigger = silent` 时私聊仍不回复。
- **风险**：私聊流量会真正进入 LLM，注意 T11 的限流与 token 预算是否足够。

### T02 · 补齐链路关键节点运行日志

- **优先级**：P0　**来源**：TODO 问题 3 根因 A
- **现象**：运行日志页只有 3 行启动日志，无任何消息处理记录。
- **根因**：`src/main.ts:79` 只把 `kind:'log'` 事件喂给 `LogService`；正常链路的 `src/pipeline/index.ts:133`（`kind:'message'`）与 `src/llm/gateway.ts:108`（`kind:'llm_call'`）只落库不写日志；`kind:'log'` 仅出现在 `pipeline/index.ts:124-130` 发送失败、`connection-manager.ts` 恢复失败等异常分支。
- **改动清单**（在 `Pipeline.handle()` 内按节点 `emit({kind:'log', source:'pipeline', ...})`）
  1. 收到消息：`收到消息 channel/from/group/长度`（INFO，含 `connectionId`）。
  2. 触发判定：通过时 `触发通过（mode=xx）`；未通过由 T03 记 DEBUG。
  3. 名单判定：通过/拦截。
  4. 限流与超长：命中时记 WARN（保留现有 `abuse` 打点，日志是补充不是替代）。
  5. LLM 请求：`调用 LLM model=xx 尝试=1`；结果 `LLM 返回 ok/耗时/token`（INFO）；失败 `LLM 失败 HTTP xxx`（ERROR，带 `res.error`）。
  6. 回复发送：`回复已发送 长度=xx 耗时=xx`；失败沿用现有 WARN。
- **实现要点**
  - 抽一个私有方法 `private log(level, msg, meta?)`，内部 `this.d.emit({kind:'log', connectionId, source:'pipeline', level, msg, meta})`，避免每处重复拼装。
  - LLM 侧日志在 `src/llm/gateway.ts` 的 `report()` 里同步补一条，`source:'llm'`，失败时 `level:'ERROR'` 且带 `error` 字段。
  - 日志量控制：`message_log` 已有全量落库，运行日志只记**关键节点**，不要逐字打印消息正文（避免隐私泄漏与文件膨胀）；正文只记长度。
- **验收标准**
  - [ ] 一次完整对话后，运行日志可读出一条完整链路：`收到消息 → 触发通过 → LLM 调用 → 回复已发送`。
  - [ ] 关闭 LLM 后端后，日志出现 ERROR（连接失败/模型不存在），不再出现「running 但静默」。
  - [ ] 按连接筛选、按 `source=pipeline/llm` 筛选均能正确命中。
- **风险**：日志文件体积上升，需配合 `storage.logRetentionDays`（已有清理定时器）。

### T07 · 本地接口不做密钥脱敏

- **优先级**：P1　**来源**：TODO 问题 1
- **现象**：核心配置页 API Key 一保存就变 `***`，再次保存报错。
- **根因**：`src/server/routes/index.ts:323-328` 的 `maskConfig()` 被 `GET /api/config`(:103)、`PUT`(:114)、`import`(:140)、`export`(:128) 全部复用；`src/services/config.service.ts:66-68` 依赖「前端回传 `***` 表示保持不变」来还原旧值。本地桌面场景下这套往返多余，且 `***` 一旦被当成真实值参与校验/加密就会报错。
- **改动清单**
  1. `routes/index.ts:103/114/140`：返回 `d.config.load()` 原始对象（已是解密后的真实值），不再 `maskConfig`。
  2. `routes/index.ts:128`（export）：保留 `maskConfig`，并支持 query `?reveal=1` 导出明文（默认脱敏）。
  3. `routes/index.ts:131-145`（import）：导入前若检测到密钥字段为 `***`，**不**用旧值覆盖，而是置空并返回提示「导入文件已脱敏，请重新填写密钥」——避免「导入了别人的脱敏配置，结果沿用本机旧 Key」的隐式错误。
  4. `config.service.ts:66-68`：`***` 还原逻辑保留作为兜底，但在 T07 之后应视为异常路径，命中时 `console.warn` 一次便于发现残留调用。
- **安全前提**：服务默认只监听 `127.0.0.1`（`src/main.ts:148`），`allowLan` 需显式开启且强制 ≥8 位访问令牌（`config.service.ts:70-72`），因此本地明文回显可接受。
- **验收标准**
  - [ ] 保存后 API Key 输入框显示真实值（配合 T08 可切明文）。
  - [ ] 连续点击保存 3 次无报错，`data/config.json` 中密钥未被重复加密或损坏。
  - [ ] `GET /api/config/export` 默认仍脱敏；`?reveal=1` 为明文。
  - [ ] 开启 `allowLan` 且令牌 < 8 位时仍被拦截。

### T12 · 同会话消息串行化

- **优先级**：P2　**来源**：代码走查新增
- **问题**：`src/manager/runtime.ts:77-79` 是 `void this.pipeline.handle(m)`，同一用户连发两条会并发跑 LLM：回复顺序错乱，且 `pipeline/index.ts:104` 的 `buf.push` 顺序与真实对话顺序不一致。
- **改动清单**
  1. 新增 `src/utils/serial-queue.ts`：`class SerialQueue { run(key, task) }`，同 key 串行、不同 key 并行，任务异常不影响后续，`finally` 清理空队列（防内存泄漏）。
  2. `runtime.ts` 增加 `private queues = new SerialQueue()`，`onMessage` 改为 `this.queues.run(\`${m.channel}:${m.groupId ?? m.fromId}\`, () => this.pipeline.handle(m))`。
  3. 队列积压超过阈值（如 5）时丢弃并记 WARN，避免 LLM 慢导致无限堆积。
- **验收标准**
  - [ ] 同一用户快速发 3 条，回复顺序与发送顺序一致，上下文不乱。
  - [ ] 两个用户并发发送互不阻塞。
  - [ ] 长跑 1 小时后 `queues` 内部 Map 为空（无泄漏）。
- **风险**：串行会拉高单用户感知延迟，需在 WARN 日志里暴露排队时长。
