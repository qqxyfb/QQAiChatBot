## P0 · 问题 3：配置完成、连接 running，但运行日志空白且给 Bot 发消息无任何反应（严重）

### 3.1 现象
- 连接 `铃铃bot` 显示启动成功 / running，LLM 已配置。
- 「运行日志」页面**没有任何内容**。
- 给 Bot 发消息**完全没有回复**（不是回复兜底语，而是完全静默）。

### 3.2 日志分析结论（实测数据）

**① 数据库侧证据（`client.db`）：**

| 表 | 行数 | 说明 |
|---|---|---|
| `message_log` | **0** | 没有任何消息进入/流出记录 |
| `llm_call` | **0** | LLM 从未被调用 |
| `abuse_event` | **0** | 没有被限流/安全检查拦截 |
| `token_budget` | 0 | — |
| `connection_event` | 5 | 有连接生命周期事件 |
| `run_session` | 1 | 会话 id=1，`model=deepseek-chat`，start→end 约 **7.6 分钟** |

- `connection_event`：`connect` @ `1792427431812` → `disconnect` @ `1792427890832`。
- 结论：**WebSocket 确实连上了并存活了约 7.6 分钟，但期间没有任何消息进入 pipeline。**
  若消息进了 pipeline，即使 LLM 失败也会写 `message_log`（兜底回复）并产生 `llm_call`；两者均为 0，说明消息在**进入 pipeline 之前**就被丢弃了。

**② 日志文件侧证据：**

`data/logs/server/server/2026-10-20.log` 每次启动只有 3 行：

```
{"seq":1,...,"msg":"前端静态资源目录：..."}
{"seq":2,...,"msg":"服务已启动：http://127.0.0.1:8700"}
{"seq":3,...,"msg":"检测到最新版本：0.1.2"}
```

- 没有任何「收到消息 / 触发判定 / 调用 LLM / 回复」记录。

### 3.3 根因

**根因 A（运行日志为空——设计缺陷）**
- `src/services/log.service.ts` 的 `LogService` 只接收 `LogEvent`（`kind:'log'`）。
- `src/main.ts:79` 仅 `bus.on('log', (e) => logService.ingest(e))` 接入。
- 而正常链路 `src/pipeline/index.ts:133` 发出的是 `kind:'message'`，`src/llm/gateway.ts:108` 发出的是 `kind:'llm_call'` —— 这两个事件只写数据库（`main.ts:73-74`），**不写运行日志**。
- 全代码中 `kind:'log'` 只在异常分支产生（如 `pipeline/index.ts:124-130` 发送失败、`connection-manager.ts:100-106` 恢复失败）。
- 因此：**正常运行 = 运行日志永远空白**，与用户预期「应有消息处理日志」直接冲突。

**根因 B（发消息无反应——消息被静默丢弃）**
1. **主因（高置信）**：连接触发规则 `trigger = "at"`（`config_json.chat.trigger`）。`src/pipeline/steps.ts:20` 中 `at` 模式仅当 `m.atBot === true` 才继续。
   而 `src/connectors/official.ts:160-170`：
   - `GROUP_AT_MESSAGE_CREATE` → `atBot: true`
   - `C2C_MESSAGE_CREATE`（私聊）→ **`atBot: false`**
   即：**私聊消息在 `at` 模式下必然被静默丢弃**（`steps.ts:20` 返回 false，且不产生任何日志/事件）。这与「发消息没反应」高度吻合。
2. **次因**：群消息必须是 `@Bot` 才会触发 `GROUP_AT_MESSAGE_CREATE`；若群里没 @ 或 Bot 未入群/无权限，事件不会到达。
3. **叠加故障（即使链路打通也会失败）**：
   - LLM 后端 `http://127.0.0.1:7863/v1`（wb2api）**当前未运行**，实测 `curl` 返回 `connection refused (os error 10061)`。
   - `run_session` 记录 `model=deepseek-chat`，但当前全局模型为 `deepseek-v4.1-flash`；需确认该模型在代理 `/v1/models` 中真实存在，否则会 400。
   - 这两点只会导致「兜底回复」，不会导致「完全静默」——但会掩盖真正问题。

### 3.4 修复建议
- [ ] **C2C 私聊不应受 `at` 规则限制**：`steps.ts` 中 `at` 模式改为 `m.channel === 'c2c' || m.atBot`；或在 `official.ts` 对 C2C 设 `atBot: true`（二选一，建议前者语义更清晰）。
- [ ] **补齐链路日志**：在 pipeline 的关键节点（收到消息 / 触发判定结果 / 名单判定 / 限流 / 安全拦截 / LLM 请求与结果 / 回复发送）统一 `emit({kind:'log', source:'pipeline'|'llm', ...})`。
- [ ] **早退原因可见**：`TriggerDecision` / `AccessControl` / `RateLimiter` 返回 false 时记录 DEBUG 级日志（含 reason），避免「静默丢弃」。
- [ ] **启动前置校验**：启动连接前探测 LLM `baseUrl` 连通性与模型是否存在于 `/v1/models`，失败直接阻断启动并提示（而非 running 后静默失败）。
- [ ] **日志文件启动时回灌**：`LogService` 构造时可读取当日 `logs/**/*.log` 回填缓冲，避免重启后页面全空。
- [ ] 顺带修复日志目录嵌套：`log.service.ts:71` 用 `connectionId || 'server'` + `source='server'` 生成 `logs/server/server/`，建议服务级日志直接落 `logs/server/`。

### 3.5 验收标准
- 私聊 Bot 发送任意文本，**必有回复**（正常回复或明确兜底语）。
- 「运行日志」能看到完整链路：`收到消息 → 触发通过 → LLM 调用(耗时/token) → 回复已发送`。
- 关闭 LLM 后端时，日志出现明确 ERROR（连接失败/模型不存在），且不出现「running 但静默」。

## P1 · 问题 1：核心配置页 API Key 接口级脱敏导致回显 `***`、二次保存出错

### 1.1 现象
- 「核心配置」页 API Key 一保存就变成 `***`。
- 再次点击保存报错。

### 1.2 根因
- `src/server/routes/index.ts:323-327` `maskConfig()` 在 **GET/PUT/import/export 响应**中把 `llm.apiKey`、`server.accessToken`、`update.pat` 一律替换为 `***`（`index.ts:103/114/128/140`）。
- `src/services/config.service.ts:65-68` 的 `save()` 依赖「前端回传 `***` 表示保持不变」来还原旧值。
- 这套「脱敏回显 + `***` 占位还原」的往返在本地桌面场景下多余且脆弱：前端把 `***` 当真实值回填，二次保存/校验时容易出现「`***` 被当作新密钥加密」或校验不一致，从而报错（`config.service.ts:70-79`）。

### 1.3 修复建议
- [ ] **本地桌面应用不做接口级脱敏**：`GET /api/config` 返回**解密后的真实值**（仅 `127.0.0.1` 本地访问，本身已有 no-LAN 保护）。
- [ ] 保留 `maskConfig` 仅用于 `/api/config/export`（导出文件可脱敏），或增加 `revealSecrets` 配置项，默认 `true`（本地）。
- [ ] 前端 `ConfigPage.tsx:75-77` 的 `Input.Password` 增加「显示/隐藏」切换，便于核对真实 Key。
- [ ] `save()` 中 `***` 兼容逻辑保留作为兜底，但不再作为正常路径。

### 1.4 验收标准
- 保存后 API Key 输入框仍显示**真实值**（可切换明文）。
- 连续点击保存 3 次，无报错，配置文件密钥不被重复加密/损坏。
- 导出配置时仍可选择是否脱敏。

## P1 · 问题 2：连接配置抽屉易误触关闭，导致编辑内容丢失

### 2.1 现象
- 在「连接管理 → 配置」抽屉中编辑时，点击**左侧遮罩区域**会关闭抽屉，未保存内容丢失，需重新编辑。

### 2.2 根因
- `web/src/pages/ConnectionsPage.tsx:311-315`：
  ```tsx
  <Drawer width={680} open={!!detail} onClose={() => setDetail(null)} ...>
  ```
- 未设置 `maskClosable` / `keyboard`，Ant Design 默认 `maskClosable=true`、`keyboard=true`。抽屉在右侧，**左侧即遮罩**，点击即关闭；按 ESC 也会关闭。

### 2.3 修复建议
- [ ] `Drawer` 增加 `maskClosable={false}`、`keyboard={false}`。
- [ ] 增加「脏检查」：表单有未保存修改时，点右上角关闭或点「取消」弹二次确认（`Modal.confirm`「放弃未保存的修改？」）。
- [ ] 可选：将 `onClose` 改为先判断 `detailForm.isFieldsTouched()`，再决定是否直接关闭。

### 2.4 验收标准
- 点击抽屉左侧遮罩区域**不会关闭**抽屉。
- 按 ESC **不会**误关闭。
- 有未保存改动时关闭会二次确认。

## P2 · 问题 4：页面强制黑色主题、侧边栏与右侧背景过于接近，费眼；需美化或主题切换

### 4.1 现象
- 页面固定黑色主题。
- 左侧菜单栏背景与右侧内容区色调接近，对比度低，长时间使用眼睛疲劳。

### 4.2 根因
- `web/src/main.tsx:10` 硬编码 `theme={{ algorithm: theme.darkAlgorithm }}`，全局强制暗色，无切换入口。
- `web/src/App.tsx:73` `<Layout.Sider theme="dark">`，`:90` `Layout.Header background:'#141414'` —— 侧边栏/顶栏/内容区均为深灰，层次不清（Ant Design 暗色默认 Sider `#001529`，但内容区 `#000/#141414` 与之对比不足）。

### 4.3 修复建议
- [ ] 引入**主题切换**（浅色 / 深色 / 跟随系统），默认**浅色**：
  - `ConfigProvider` 的 `algorithm` 改为由 state 控制（`theme.defaultAlgorithm` / `theme.darkAlgorithm`）。
  - 选择结果持久化到 `localStorage`（如 `qqab.theme`）。
  - 在顶栏右侧放置主题切换按钮（`Segmented` 或 `Switch`）。
- [ ] 提升层次对比：
  - 浅色：Sider 用白底 + 右侧 1px 分隔线，或深色 Sider（`#001529`）+ 浅色内容区 `#f5f5f5`。
  - 深色：Sider `#001529`，内容区 `#141414`，Header 加 `borderBottom` 分隔。
- [ ] 统一页面背景/卡片圆角/间距，卡片在内容区上浮（`box-shadow` 或描边）。
- [ ] 检查「运行日志 / 数据统计 / 使用消耗」图表在浅色下的文字与网格线颜色。

### 4.4 验收标准
- 顶栏可一键切换浅色/深色，刷新后保持上次选择。
- 浅色模式下侧边栏与内容区**边界清晰**，正文对比度符合 WCAG AA。
- 图表、表格、表单在两种主题下均可读。

## 2026-10-21 追加（待做）· 上下文说话人归属 / 群聊插话判断

> 现象：回复经常搞错上下文、多人时不区分谁说的、随机聊天会接别人之间的对话。
> 结论：不是模型问题，是**上下文里根本没有「谁说的」这个信息**，加上 @ 判定过宽、随机触发只看概率。

### 一、代码级分析（现状与根因）

1. **上下文不记录说话人（核心）**
   - `src/pipeline/context.ts:1-4` `ContextItem` 只有 `role/content`；`src/pipeline/index.ts:232` 把**所有人**的消息都 push 成 `role:'user'`。
   - `src/pipeline/steps.ts:129-131` 统一渲染成「用户：/你：」——群里三个人的话全是「用户」，模型只能按最近一条猜，必然张冠李戴。
   - `src/types.ts:143-151` `NormalizedMessage` 只有 `fromId`，没有昵称/群名片；`src/connectors/account.ts:226-234` 也没读 `sender.card / sender.nickname`。**信息在源头就丢了，靠 prompt 补救不回来。**

2. **@ 判定过宽（乱接话的直接原因之一）**
   - `src/connectors/account.ts:233`：`atBot: raw.includes('[CQ:at,qq=')` —— 群里 **@ 任何人**都算 @ 了机器人，机器人会接「@张三」的话并引用回复。
   - 没有与 `self_id`（登录 QQ）比对；正向/反向 WS 事件里都有 `self_id`，目前未保存。

3. **无法识别「这句话是不是在回复机器人」**
   - 入站消息里的 `[CQ:reply,id=xxx]` 没有解析；`sendReply`（`account.ts:237-246`）只 `send` 不读回执，**机器人发言的 message_id 一个都没存**，所以无法判断用户是否在回机器人。

4. **随机模式只看概率、不看对象**
   - `src/pipeline/steps.ts:36-41` random 分支只有 `Math.random() < p`，任何群消息都可能被接，包括 A 对 B 说的、和机器人完全无关的。
   - 被随机触发后 `ReplyQuote` 只在 `atBot` 时才引用（`steps.ts:63-71`），插话既不引用也看不出在回谁。

5. **上下文里只有「机器人参与过的对话」**
   - 未触发的消息在 `src/pipeline/index.ts:99-101` 直接 return，不写入上下文。随机插话时模型看不到前因，只能凭最后一条猜，越猜越错。

6. **群上下文是「一锅烩」**
   - key = `channel:groupId`（`index.ts:125`），同群所有人共享一份 `contextMaxMessages` 缓冲；活跃用户会把别人的上下文挤掉，也没有 per-user 视角。

### 二、修复方案（按优先级）

#### P0 · 说话人归属（解决「搞错上下文」）

- [ ] `NormalizedMessage` 增加：`senderName?`（群名片优先，其次昵称）、`selfId?`、`replyToId?`、`mentionedIds?: string[]`；
      `account.ts` 从 `sender.card || sender.nickname` 取昵称，解析 `[CQ:reply,id=]` 与所有 `[CQ:at,qq=]`；官方 Bot 用 `author.member_openid / user_openid` 兜底显示名。
- [ ] `ContextItem` 增加 `sender?: { id: string; name: string; isBot?: boolean }`；`Pipeline` 写入时带上，机器人自身的回复标记 `isBot`。
- [ ] `PromptBuilder` 渲染成 `张三：…` / `你（机器人）：…`，并在提示词里明确：
      「这是一个多人群聊，每行开头是说话人；只回应最后一条的说话人，不要替别人回答，也不要重复别人说过的话」。
- [ ] 昵称清洗：去换行、截断 ≤ 12 字、重名加 `#后四位`；取不到昵称时用 `用户+fromId 后四位`。
- [ ] 新增 `contextScope: 'group' | 'per_user'`（默认 `group` + 说话人标签；`per_user` 时 key 追加 `fromId`，适合一对一客服场景）。
- [ ] `contextMaxMessages` 按「消息条数」改为按「对话轮数 × 人数」折算，避免人多的群上下文过短。

#### P0 · @ 判定与「回复机器人」（解决「该不该接」）

- [ ] `atBot` 改为 `mentionedIds.includes(selfId)`；明确排除「@ 了别人但没 @ 机器人」。拿不到 `selfId` 时降级旧逻辑并打 WARN，不能因此完全不回。
- [ ] `sendReply` 读取 OneBot echo 回执，把返回的 `message_id` 记入 `botMessageIds`（LRU，容量 200）；`replyToId` 命中即视为「在回复机器人」。
- [ ] 触发优先级：`被@机器人` > `回复机器人消息` > `关键词命中` > `概率插话`；前两者在 random 模式下也必须直接触发。
- [ ] 引用策略补充：随机插话也带引用（否则不知道在回谁）；「@ 别人」的消息永不引用。

#### P1 · 随机插话收敛（解决「插别人话」）

- [ ] random 增加 engagement 前置条件，满足任一才接：① 最近 N 分钟机器人在本群说过话；② 消息含问句/「你、你们、在吗、机器人名」；③ 该消息是回复机器人的。新增配置 `interjectPolicy: 'off' | 'smart' | 'loose'`（默认 smart）。
- [ ] 群聊维护「旁听缓冲」（只听不回）：未触发消息写入独立 `ambient` 缓冲，仅用于插话前判断与后续可能的多轮上下文，不直接进 prompt（控 token）。
- [ ] 同人连发抑制：某人连续发言、或机器人刚回过且无人接话时，降低/取消概率触发（例如 20s 内不重复接同一人）。
- [ ] 可选轻量判定：仅对高概率候选发一次 `max_tokens=8` 的小请求（「这句话在对谁说？是否在问机器人？」），可关闭以省钱。

#### P2 · 可观测与调参

- [ ] 日志记录触发依据（被@ / 回复机器人 / 关键词 / 概率 + 命中的 engagement 条件）与说话人，便于复盘「为什么插话」。
- [ ] 数据统计增加「被 @ 次数 / 插话次数 / 人工标记误插话」，用于调 engagement 阈值。

### 三、验收标准

- 群里 A、B 交替发言后 @ 机器人：回复内容只针对当前说话人，不复述他人的观点，不把 A 的话当 B 说的。
- `@张三` 不触发；`@机器人` 必然触发；回复机器人的消息必然触发（即使没 @）。
- 随机模式下纯 A↔B 对话被打断的次数明显下降；一旦插话必带引用。
- 上下文里能直接看到 `张三：…` / `李四：…` / `你（机器人）：…`（日志 DEBUG 可查）。

### 四、风险与取舍

- 昵称注入会占 token（每条约 6~10 token），人多时需要按轮数折算上限。
- `per_user` 会丢失群氛围，默认不开。
- 部分中转/反向 WS 可能拿不到 `self_id` 或 `sender` 字段，必须具备降级路径，且降级后行为要与现在一致（不能更差）。
- 「回复机器人」依赖 OneBot 回执；若实现不返回 `message_id`，则退化为「仅 @ 触发」。
